Coverage notes:

- Coverage is fragmented across product areas. The Cloud Adoption Framework supplies the architecture and decision reasoning, while Azure management groups, Azure Resource Manager, Azure Policy, and Azure RBAC define the enforceable mechanics.
- Download the Cloud Adoption Framework first, especially resource organization, management groups, subscriptions, design principles, application environments, subscription vending, and tagging. Follow with Azure Resource Manager, Azure management groups, and Azure Policy; add Cost Management when chargeback or showback is part of the scenario.
- Use management groups for subscriptions that require common policy and access archetypes, subscriptions as workload or platform management and scale boundaries, and resource groups for resources that share lifecycle and administration. Use tags for cross-hierarchy metadata instead of recreating the organization chart in a deep tree.
- Remember the core limits and boundaries: management-group trees support six levels below the tenant root, a directory supports 10,000 management groups, each node has one parent, most scopes support 50 tag pairs, and a resource group generally supports 800 instances of a resource type.
- Tags do not inherit natively and management groups cannot be tagged. Use Azure Policy `modify` with remediation when existing resource tags must be corrected; Cost Management tag inheritance changes usage records only, not the resources.
- Distinguish adjacent controls: Azure Policy governs resource state, Azure RBAC governs who can act, and resource locks protect control-plane changes or deletion. Avoid management groups for dev/test/prod or for regions unless their policy, access, sovereignty, or residency requirements truly differ.
- Azure Resource Graph, naming conventions, subscription vending, tenant-transfer restrictions, billing hierarchies, resource locks, quota planning, and infrastructure-as-code landing-zone modules are supporting topics and should not dominate this task map.
