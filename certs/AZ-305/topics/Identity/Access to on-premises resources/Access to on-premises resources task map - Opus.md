Forum-discovery note: Public candidate discussions for this task recur around a small set of scenario shapes: publishing an internal web app to remote or partner users without a VPN, adding MFA or Conditional Access to a legacy Windows-integrated-authentication app, lifting a legacy LDAP/Kerberos app into Azure and choosing between Microsoft Entra Domain Services and self-managed domain controllers, authorizing on-premises file share access from Azure, and granting time-bound administrative access to on-premises servers. Reddit, Microsoft Q&A, and Microsoft Tech Community threads were used only as discovery signals; every product listed here was validated against official Microsoft documentation before inclusion.

Coverage notes:

- This task is fragmented rather than served by one documentation set. There is no single "authorize access to on-premises resources" product page. Application proxy is the closest thing to a primary set, but a complete recommendation also spans Private Access, Domain Services versus AD DS, hybrid group provisioning, and identity governance.
- Read the scenario for what is being accessed. A web app points to Application Proxy; a non-HTTP resource such as RDP, SSH, SMB, or LDAP points to Microsoft Entra Private Access; a legacy app needing Kerberos/NTLM or LDAP bind points to Microsoft Entra Domain Services or self-managed AD DS; an on-premises server itself points to Azure Arc-enabled servers; an SMB share points to Azure Files identity-based authentication.
- The strongest distractor pattern is a network answer to an identity question. VPN Gateway and ExpressRoute provide reachability, not authorization. When the requirement is per-user, per-app, MFA-enforced, or auditable access, the answer is Application Proxy or Private Access, not a site-to-site tunnel.
- Know the Domain Services boundaries cold, because they are the deciding facts in comparison questions: no Domain Admin or Enterprise Admin rights, no schema extensions, resource-based KCD only, one-way sync from Microsoft Entra ID (no write-back to on-premises AD), forest trusts require the Enterprise SKU, and federated-only accounts have no usable password hash so they cannot authenticate.
- Distinguish this task from the sibling "authorizing access to Azure resources" task. That one is dominated by Azure RBAC, PIM for Azure resource roles, and managed identities. This one is dominated by Application Proxy, Private Access, hybrid identity plumbing, and AD DS group membership, because the authorization decision is ultimately enforced by an on-premises directory or an on-premises application.
- Download first: Application proxy, Global Secure Access, and Microsoft Entra Domain Services. Add Hybrid identity and Microsoft Entra ID Governance when the scenario mentions group-based app access, approvals, or recertification. Add Azure Files and Azure Arc-enabled servers when the resource is a file share or a server rather than an application.
- Architecture guidance beats product overviews for the recommend-style wording. The Cloud Adoption Framework hybrid identity design area and the Well-Architected Framework security pillar explain which option to choose and why, whereas the product pages explain how each one works.
- Testable but only lightly covered here: AD FS retirement and migrating federated apps to Microsoft Entra ID, Kerberos Constrained Delegation troubleshooting details, Microsoft Entra hybrid join as a prerequisite for device-based Conditional Access on domain-joined machines, cloud Kerberos trust for Windows Hello for Business accessing on-premises resources, Private Access for domain controller traffic, Azure Bastion plus just-in-time access for jump-host patterns, and the Microsoft Entra Suite licensing bundle that Private Access and ID Governance depend on.
