## Azure Key Vault Managed HSM

**Classification:** Core  
**Why it matters:** Managed HSM is the managed, Azure-integrated answer when keys require single-tenant isolation, customer-controlled recovery material, and strong key sovereignty without customer administration of an HSM cluster.  
**Primary Microsoft source:** [Managed HSM overview](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/overview)  
**Limits and quotas source:** [Managed HSM service limits](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/service-limits)

### Deep technical facts / requirements

1. **[Protection and tenancy]** Every key in Managed HSM is protected by FIPS 140-3 Level 3 validated hardware in an isolated single-tenant pool and security domain; Managed HSM has no software-key tier. [Managed HSM key protection](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/about-keys).
2. **[Object incompatibility]** Managed HSM stores cryptographic keys only: it does not store Key Vault secret objects or manage X.509 certificate lifecycle. RSA-HSM supports `2,048`, `3,072`, and `4,096` bits; EC-HSM supports P-256, P-256K, P-384, and P-521; oct-HSM supports AES `128`, `192`, and `256` bits. [Managed HSM key types and sizes](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/about-keys#supported-key-types-and-sizes).
3. **[Object limits]** One Managed HSM instance supports `5,000` keys and `100` versions per key. A subscription can hold `5` instances per region by default, so fleet and version-growth requirements can force quota planning or additional subscriptions. [Managed HSM object limits](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/service-limits#object-limits).
4. **[Authorization limits]** One instance supports `50` custom local role definitions, `50` role assignments at HSM scope, and `10` role assignments at each individual-key scope. Designing one key assignment per workload can therefore hit a hard limit sooner than vault-scoped role design. [Managed HSM role limits](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/service-limits#object-limits).
5. **[Control plane versus data plane]** The control plane uses Azure RBAC at `management.azure.com:443`; key operations, local role management, backup/restore, and security-domain operations use Managed HSM local RBAC at `<name>.managedhsm.azure.net:443`. A control-plane Contributor assignment does not grant key use. [Managed HSM access-control endpoints](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/access-control#resource-endpoints).
6. **[Provisioning dependency]** Creation is a two-stage process: provision the Azure resource, then activate it by downloading and protecting its security domain. The instance is not operational for key workloads until activation completes. [Managed HSM provisioning and activation](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/quick-create-portal).
7. **[Recovery custody]** At least `3` RSA recovery key pairs are required to initialize the security domain, and a customer-defined quorum is required for recovery. The security-domain file, quorum private keys, and an HSM backup are separate artifacts; losing the domain or quorum makes recovery impossible and Microsoft cannot reconstruct them. [Managed HSM key-recovery responsibilities](https://learn.microsoft.com/en-us/azure/azure-sovereign-clouds/public/key-recovery-management).
8. **[Networking]** Managed HSM supports Private Link but not virtual-network service endpoints. The private endpoint and VNet must be in the same region, although the Managed HSM resource can be in another region, and the exact private DNS zone is `privatelink.managedhsm.azure.net`. [Managed HSM Private Link requirements](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/private-link).
9. **[Deletion and billing]** Soft delete cannot be disabled; retention is `7–90` days and defaults to `90`. A soft-deleted Managed HSM continues to incur its full hourly charge until it is purged or retention expires. [Managed HSM soft-delete behavior](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/soft-delete-overview).
10. **[Backup dependency]** Full backup includes keys, versions, attributes, tags, and local role assignments. The supported managed-identity path requires a user-assigned managed identity with Storage Blob Data Contributor on the backup account, and the storage account cannot have an immutability policy. [Managed HSM full-backup prerequisites](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/backup-restore#prerequisites-for-backing-up-and-restoring-by-using-user-assigned-managed-identity).
11. **[Restore behavior]** Full restore is destructive: it removes current HSM contents, restores the backup state, and disables all other data-plane commands while the HSM is in restore mode. A full backup of the destination must have completed at least `30` minutes before restore, and source and destination must share the same security domain. [Managed HSM full-restore behavior](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/backup-restore#full-restore).
12. **[Disaster recovery]** A customer can recreate a Managed HSM in the same or another region only with the source security domain, at least the configured quorum of recovery private keys, and a current full backup. The restored instance receives the backed-up keys and local role assignments, not an automatically live-replicated application endpoint. [Managed HSM disaster-recovery process](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/disaster-recovery-guide).
13. **[Key attestation]** Managed HSM can attest that a key was generated and resides inside a Microsoft-operated HSM; asymmetric keys have public and private attestation, while symmetric oct-HSM keys have private attestation only. [Managed HSM key attestation](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/about-keys#key-attestation).
14. **[Preview status]** **[Preview]** External key management keeps KEK material in a customer-operated HSM outside Microsoft infrastructure but supports only `wrapKey` and `unwrapKey`, adds proxy/HSM latency, requires customer-managed mTLS/networking/logging, and carries no Managed HSM SLA for the external key. [Managed HSM external key management comparison](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/external-key-management-overview#comparison-external-keys-versus-managed-hsm-keys).

### Incompatibilities and mutual exclusions

If a requirement includes passwords, connection strings, or automated certificate issuance together with single-tenant HSM keys, Managed HSM cannot be the sole store because it supports HSM-protected keys only; add Key Vault for the nonkey objects or revise the boundary. [Managed HSM object support](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/about-keys) [Key Vault object types](https://learn.microsoft.com/en-us/azure/key-vault/general/about-keys-secrets-certificates#object-types).

If the backup storage account has an immutability policy, the supported Managed HSM full-backup workflow cannot use it; choose a compatible backup account and protect the blobs through supported RBAC/network controls. [Managed HSM backup unsupported configuration](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/backup-restore#prerequisites-for-backing-up-and-restoring-by-using-user-assigned-managed-identity).

### Edge cases and gotchas

- Recovering a deleted Managed HSM does not restore its deleted private endpoint; the private endpoint must be recreated. [Managed HSM Private Link recovery note](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/private-link).
- The security domain is not a backup of the keys; successful disaster recovery requires both the security-domain/quorum material and a separate current HSM backup. [Managed HSM key-recovery responsibilities](https://learn.microsoft.com/en-us/azure/azure-sovereign-clouds/public/key-recovery-management).
- A backup storage account encrypted by a CMK that exists only in the failed Managed HSM can create a circular recovery dependency; Microsoft recommends platform-managed keys, a Key Vault Premium key, or another independently available key for that backup account. [Managed HSM sovereign-recovery guidance](https://learn.microsoft.com/en-us/azure/azure-sovereign-clouds/public/key-recovery-management#take-regular-secure-hsm-backups).
- Trusted-service bypass permits only documented Azure service scenarios and still requires local RBAC; enabling the bypass does not grant cryptographic permission. [Managed HSM trusted-services behavior](https://learn.microsoft.com/en-us/azure/key-vault/managed-hsm/private-link#allow-trusted-services-to-access-managed-hsm).

### AZ-305 exam discriminator

Choose Managed HSM when the decisive combination is HSM-protected keys, single tenancy/key sovereignty, and a supported Azure PaaS CMK or managed cryptographic interface. Reject it for mixed secrets/certificates or general native PKCS#11 lift-and-shift. [Azure key-management selection guide](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose).

### Common trap

The words “fully managed” do not transfer recovery custody to Microsoft: the customer must protect the security domain, quorum private keys, and backups, and Microsoft cannot recover a lost quorum. [Managed HSM security-domain responsibility](https://learn.microsoft.com/en-us/azure/azure-sovereign-clouds/public/key-recovery-management).

## Azure Cloud HSM

**Classification:** Core  
**Why it matters:** Cloud HSM is the customer-administered, native-interface option for VM and lift-and-shift applications that cannot use the Key Vault REST model.  
**Primary Microsoft source:** [Azure Cloud HSM overview](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview)  
**Limits and quotas source:** [Azure Cloud HSM service limits](https://learn.microsoft.com/en-us/azure/cloud-hsm/service-limits)

### Deep technical facts / requirements

1. **[Tenancy and control]** Cloud HSM is a FIPS 140-3 Level 3 validated, single-tenant service in which the customer retains complete HSM administrative authority while Microsoft operates cluster availability, patching, and hardware maintenance. [Cloud HSM overview](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview).
2. **[Cluster topology and resiliency]** Every Cloud HSM cluster contains `3` HSM nodes; the service synchronizes keys and policies, load-balances cryptographic operations, and migrates an unavailable member to healthy hardware. [Cloud HSM cluster architecture](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#customer-owned-highly-available-single-tenant-hsm-as-a-service).
3. **[Interface compatibility]** Cloud HSM supports PKCS#11, OpenSSL, JCA/JCE, CNG/KSP, AD CS private-key protection, Apache/NGINX/F5 TLS offload, SQL Server or Oracle TDE, and document/code signing. It is IaaS-oriented and exposes native cryptographic interfaces rather than the Key Vault object REST model. [Cloud HSM supported integrations](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#azure-cloud-hsm-suitability).
4. **[Object limits]** One Cloud HSM supports a maximum of `3,200` key handles: an RSA or EC key consumes `2` handles, yielding at most `1,600` RSA or `1,600` EC keys, while an AES key consumes `1` handle, yielding at most `3,200` AES keys. Mixed key types consume the shared handle budget. [Cloud HSM service limits](https://learn.microsoft.com/en-us/azure/cloud-hsm/service-limits#object-limits).
5. **[Authentication]** Cloud HSM supports password-based HSM authentication only and does not support a PIN entry device. PKCS#11 applications call `C_Login` once per cluster slot and can then open additional sessions without another login. [Cloud HSM authentication methods](https://learn.microsoft.com/en-us/azure/cloud-hsm/authentication#supported-authentication-methods).
6. **[Password and administration constraints]** HSM passwords must be `8–32` characters; Microsoft recommends at least `12`. Microsoft does not retain customer HSM credentials and recommends at least `2` administrators because loss of the only administrator credential can cause unrecoverable lockout. [Cloud HSM user-management guidance](https://learn.microsoft.com/en-us/azure/cloud-hsm/user-management#use-strong-passwords).
7. **[User synchronization edge]** User creation targets all `3` nodes when healthy, but Cloud HSM does not provide backend user synchronization. A user missing from one node can cause authentication failures when traffic reaches that node, so customers must verify and repair user presence across all nodes. [Cloud HSM user synchronization](https://learn.microsoft.com/en-us/azure/cloud-hsm/user-management#ensure-your-hsm-users-are-available-on-all-nodes-of-your-cluster).
8. **[Networking and ports]** Cloud HSM is reached privately from VNets. The service listens on `443` for client requests, `444` for management-tool requests, and `445` for server-to-server communication; customer-facing TCP-over-TLS front-end ports are `2224` and `2225`. [Cloud HSM networking ports](https://learn.microsoft.com/en-us/azure/cloud-hsm/troubleshoot#what-is-the-recommended-way-of-connecting-to-cloud-hsm-from-the-corporate-network-operationadmin-tasks).
9. **[Client runtime dependency]** PKCS#11 and other provider applications require `azcloudhsm_client` to run on the application host; on a host, applications share the client sessions and credentials, so an interactive utility session can block a second application's authentication. [Cloud HSM client session handling](https://learn.microsoft.com/en-us/azure/cloud-hsm/authentication#cloud-hsm-client-session-handling).
10. **[Data residency and regional flag]** **[Limited regions — verify before specifying]** Cloud HSM does not store or process customer data outside the deployment region, and availability must be checked in Azure Product Availability by Region before design commitment. [Cloud HSM data residency](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#customer-owned-highly-available-single-tenant-hsm-as-a-service) [Cloud HSM pricing and regional-availability guidance](https://azure.microsoft.com/en-us/pricing/details/azure-cloud-hsm/).
11. **[Backup identity and permissions]** Backup/restore requires Azure Blob Storage, a user-assigned managed identity, and at least Storage Blob Data Contributor; SAS-token authorization is unsupported. The backup is protected by a key derived inside the HSM that Microsoft cannot read. [Cloud HSM backup prerequisites](https://learn.microsoft.com/en-us/azure/cloud-hsm/backup-restore#prerequisites).
12. **[Restore incompatibility]** A Cloud HSM backup cannot be restored to its source or to any already activated cluster; the target must be a different nonactivated Cloud HSM, and an invalid target can be rendered nonfunctional. [Cloud HSM unsupported restore configurations](https://learn.microsoft.com/en-us/azure/cloud-hsm/backup-restore#unsupported-configurations).
13. **[Cost behavior]** Cloud HSM billing begins at resource creation, not activation, is hourly, cannot be paused or stopped, and ends only when the resource is deleted. An unused but provisioned cluster therefore continues to cost money. [Azure Cloud HSM pricing FAQ](https://azure.microsoft.com/en-us/pricing/details/azure-cloud-hsm/).
14. **[Failure handling]** Microsoft can replace a failed HSM node without a maintenance window; applications must implement client-side retry for HSM operations because transient failures can occur during replacement or maintenance. [Cloud HSM retry guidance](https://learn.microsoft.com/en-us/azure/cloud-hsm/authentication#retries-for-integration-of-hsm-operations).

### Incompatibilities and mutual exclusions

If an Azure PaaS or SaaS service requires a customer-managed key through a supported Key Vault URI, Cloud HSM cannot be the key source because it is IaaS-only and has no PaaS/SaaS CMK integration; use Key Vault Premium or Managed HSM according to tenancy requirements. [Cloud HSM not-a-fit scenarios](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#not-a-fit).

If the solution needs secret storage or automatic X.509 certificate lifecycle, Cloud HSM cannot replace Key Vault because it is neither a secret store nor a certificate-lifecycle service. [Cloud HSM suitability boundaries](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#azure-cloud-hsm-suitability).

### Edge cases and gotchas

- SQL Server EKM through Cloud HSM supports Windows Server only and asymmetric keys only; SQL Server on Linux and symmetric TDE key integration are unsupported in that provider. [Cloud HSM SQL Server EKM limitations](https://learn.microsoft.com/en-us/azure/cloud-hsm/troubleshoot#sql-server-ekm-for-azure-cloud-hsm).
- PKCS#11 multithreaded applications must initialize the library once and use a separate session per thread; sharing one session across threads is unsupported guidance. [Cloud HSM multithreading guidance](https://learn.microsoft.com/en-us/azure/cloud-hsm/authentication#multithreading-techniques).
- Key handles can change after restore even though key IDs remain stable, so applications must not treat a transient handle as the durable identifier. [Cloud HSM restore validation](https://learn.microsoft.com/en-us/azure/cloud-hsm/backup-restore#validate-the-restore-to-the-destination-cloud-hsm-resource).
- Cloud HSM automatically synchronizes keys and policies but not users; “three-node cluster” must not be mistaken for automatic identity consistency. [Cloud HSM user-management warning](https://learn.microsoft.com/en-us/azure/cloud-hsm/user-management#ensure-your-hsm-users-are-available-on-all-nodes-of-your-cluster).

### AZ-305 exam discriminator

Choose Cloud HSM when an unchanged VM/IaaS application requires native PKCS#11, JCA/JCE, CNG/KSP, AD CS, Oracle/SQL TDE, or conventional TLS offload together with customer HSM administration. [Cloud HSM best-fit scenarios](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#best-fit).

### Common trap

Cloud HSM's single tenancy and FIPS level do not make it a stronger universal CMK answer: it cannot serve Azure PaaS/SaaS CMK integrations, which eliminates it whenever the consumer expects a Key Vault/Managed HSM key URI. [Cloud HSM not-a-fit scenarios](https://learn.microsoft.com/en-us/azure/cloud-hsm/overview#not-a-fit).

## Azure Key Vault Standard and Premium

**Classification:** Core  
**Why it matters:** Standard and Premium are the default managed-vault choices when a solution needs secrets, certificates, software keys, or Azure-native cryptographic operations. Premium is a key-protection upgrade, not a different secret or certificate store.  
**Primary Microsoft source:** [Azure Key Vault overview](https://learn.microsoft.com/en-us/azure/key-vault/general/overview)  
**Limits and quotas source:** [Azure Key Vault service limits](https://learn.microsoft.com/en-us/azure/key-vault/general/service-limits)

### Deep technical facts / requirements

1. **[Object model and SKU gating]** A Standard vault stores software-protected keys, secrets, and certificates; a Premium vault stores the same object types and additionally supports HSM-protected keys. Managed HSM is a separate resource type rather than the Premium tier of a vault. [Key Vault object-type support](https://learn.microsoft.com/en-us/azure/key-vault/general/about-keys-secrets-certificates#object-types) [Azure key-management selection guide](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose).
2. **[Versioning]** Keys, secrets, and certificates are versioned objects. A versionless identifier lets a consumer resolve the current version, while a versioned identifier pins the consumer to immutable object material and must be updated deliberately. [Key Vault object identifiers and versioning](https://learn.microsoft.com/en-us/azure/key-vault/general/about-keys-secrets-certificates#object-identifiers).
3. **[Size limit]** A secret value can contain at most `25 KB`; Key Vault is therefore not a document, configuration-database, or large-binary store. Certificate PFX/PEM content is exposed through the associated secret and is subject to the vault's secret-size boundary. [Azure Key Vault service limits](https://learn.microsoft.com/en-us/azure/key-vault/general/service-limits) [Key Vault certificate composition](https://learn.microsoft.com/en-us/azure/key-vault/certificates/about-certificates#composition-of-a-certificate).
4. **[Object-count and backup limits]** A vault has no fixed maximum count of keys, secrets, or certificates, but Microsoft recommends limiting versions per object; backup supports no more than `500` prior versions of one object, so uncontrolled version growth can make that object impossible to back up. [Azure Key Vault service limits](https://learn.microsoft.com/en-us/azure/key-vault/general/service-limits) [Key Vault backup limits](https://learn.microsoft.com/en-us/azure/reliability/reliability-key-vault#backup-and-restore).
5. **[Throughput and throttling]** Key Vault applies per-vault, per-region transaction limits and returns HTTP `429` when a threshold is exceeded; the aggregate subscription limit for a transaction type is `5` times the individual-vault limit in one region. Clients must use exponential backoff, memory caching, and vault separation by security or availability domain rather than immediate retry loops. [Key Vault throttling guidance](https://learn.microsoft.com/en-us/azure/key-vault/general/overview-throttling).
6. **[High-scale secure key release]** `CREATE key` and `RELEASE key` share a throttling category limited to `10` transactions per `10` seconds for HSM-protected vault keys and `20` per `10` seconds for software-protected vault keys; Microsoft directs high-throughput secure-key-release designs to Managed HSM. [Key Vault throttling guidance](https://learn.microsoft.com/en-us/azure/key-vault/general/overview-throttling).
7. **[Key algorithms and protection]** Key Vault supports RSA and elliptic-curve keys, but supported sizes, curves, algorithms, operations, and import paths differ between software and HSM protection; a design must validate the required operation instead of treating “HSM-backed” as proof of protocol compatibility. [Key Vault key types and protection methods](https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys#key-types-and-protection-methods).
8. **[Identity and access default change]** Azure RBAC is the recommended authorization model and, starting with Key Vault API version `2026-02-01`, is the default for newly created vaults; access policies remain a legacy compatibility model. [Key Vault RBAC migration and 2026 default](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-migration).
9. **[Network default]** A newly created vault has its firewall disabled by default, so its public endpoint accepts network requests from any source; Microsoft Entra authentication and authorization still gate object operations. Network openness and data-plane permission are separate controls. [Key Vault network-security defaults](https://learn.microsoft.com/en-us/azure/key-vault/general/network-security#key-vault-firewall-disabled-default).
10. **[Firewall maximums]** A vault supports at most `200` virtual-network rules and `1,000` IPv4 CIDR rules. Firewall IP rules accept public IPv4 addresses only; IPv6 and RFC 1918 private address ranges are not supported as IP rules. [Key Vault firewall limits](https://learn.microsoft.com/en-us/azure/key-vault/general/network-security#key-vault-firewall-enabled-ipv4-addresses-and-ranges---static-ips).
11. **[Resiliency]** Standard and Premium receive the same automatic zone redundancy in availability-zone regions, with synchronous cross-zone data replication and no extra zone-redundancy charge; there is no Premium-only availability advantage. [Key Vault zone-resilience requirements and cost](https://learn.microsoft.com/en-us/azure/reliability/reliability-key-vault#resilience-to-availability-zone-failures).
12. **[Regional behavior]** A vault is a single-region resource. In most paired regions, Microsoft asynchronously replicates data and can initiate a best-effort regional failover after a significant delay; Brazil South, Brazil Southeast, West US 3, and regions without a pair do not support that Microsoft-managed cross-region failover. [Key Vault multi-region support](https://learn.microsoft.com/en-us/azure/reliability/reliability-key-vault#resilience-to-region-wide-failures).
13. **[Failover restrictions]** During Microsoft-managed regional failover, the vault can be unavailable for minutes and then operate read-only in the paired region; create, update, delete, access-policy, firewall, and property changes are unavailable until failback, even though supported get and cryptographic operations continue. [Key Vault regional-failover behavior](https://learn.microsoft.com/en-us/azure/reliability/reliability-key-vault#microsoft-managed-failover-to-a-paired-region).
14. **[Deletion defaults and maximums]** Soft delete is always enabled. Retention is set to `7–90` days, defaults to `90` days, and cannot be changed after the vault is created; purge protection uses the same interval and cannot be disabled after it is enabled. [Key Vault soft-delete and purge-protection behavior](https://learn.microsoft.com/en-us/azure/key-vault/general/soft-delete-overview).
15. **[Cost discriminator]** Standard and Premium are billed by operations, and Premium adds charges for HSM-protected keys and their operations; automatic zone redundancy and built-in paired-region replication add no separate charge. [Azure Key Vault pricing](https://azure.microsoft.com/en-us/pricing/details/key-vault/) [Key Vault reliability cost](https://learn.microsoft.com/en-us/azure/reliability/reliability-key-vault#cost).

### Incompatibilities and mutual exclusions

If secrets or certificate lifecycle and a single-tenant HSM boundary are both mandatory, neither one vault tier nor Managed HSM alone satisfies the combination: Premium remains multitenant, while Managed HSM stores only HSM-protected keys, so the architecture needs complementary stores or a changed requirement. [Azure key-management selection guide](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose) [Key Vault object support](https://learn.microsoft.com/en-us/azure/key-vault/general/about-keys-secrets-certificates#object-types).

If native PKCS#11/JCA/JCE/CNG application integration is mandatory, Key Vault Standard or Premium cannot be substituted merely because Premium uses HSMs; full native interfaces belong to Cloud HSM. [Azure key-management interface comparison](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose).

### Edge cases and gotchas

- A Key Vault certificate creates an addressable certificate object, key object, and secret object with the same name; a principal allowed to read the secret can retrieve the private-key-bearing PFX/PEM when the policy permits export. [Key Vault certificate composition](https://learn.microsoft.com/en-us/azure/key-vault/certificates/about-certificates#composition-of-a-certificate).
- A private endpoint does not make the public DNS name disappear: public DNS still resolves the vault FQDN to the shared service ingress, while `publicNetworkAccess=Disabled` rejects the request. DNS visibility is not proof of public data-plane access. [Key Vault Private Link public-DNS behavior](https://learn.microsoft.com/en-us/azure/key-vault/general/private-link-service#public-dns-visibility-of-a-private-key-vault).
- The trusted-services bypass is a documented list of scenarios rather than all Azure services. It can continue to apply when public network access is disabled, but Network Security Perimeter mode overrides it unless an explicit perimeter rule permits the traffic. [Key Vault trusted-services and perimeter restrictions](https://learn.microsoft.com/en-us/azure/key-vault/general/network-security#restrictions-and-limitations).
- Switching an existing vault from access policies to Azure RBAC immediately invalidates its access-policy permissions; equivalent role assignments must exist before cutover or workloads lose data-plane access. [Key Vault RBAC migration procedure](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide#enable-azure-rbac-permissions-on-key-vault).

### AZ-305 exam discriminator

Choose Standard for mixed software keys, secrets, and certificates; choose Premium only when a vault-compatible HSM-protected key is a hard requirement. Neither “certificate” nor “secure secret” alone requires Premium, and Premium does not satisfy single tenancy or native HSM interfaces. [Azure key-management selection guide](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose).

### Common trap

“Key Vault Contributor” sounds broad but controls the vault resource only; it grants no key, secret, or certificate data access. The workload needs a least-privilege data-plane role such as Key Vault Secrets User or a cryptographic role. [Key Vault built-in role boundary](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide#azure-built-in-roles-for-key-vault-data-plane-operations).

## Azure Payment HSM

**Classification:** Core  
**Why it matters:** Payment HSM is the industry-specific answer for real-time payment cryptography whose command set, certification, accessories, networking, and availability model differ from general-purpose HSM services.  
**Primary Microsoft source:** [Azure Payment HSM overview](https://learn.microsoft.com/en-us/azure/payment-hsm/overview)  
**Limits and quotas source:** [Azure Payment HSM service support guide](https://learn.microsoft.com/en-us/azure/payment-hsm/support-guide)

### Deep technical facts / requirements

1. **[Hardware and workload scope]** Payment HSM is a bare-metal service built on Thales payShield 10K devices for payment authorization, PIN/EMV cryptogram validation, 3-D Secure, card/mobile credential issuing, remote key loading, P2PE, and payment tokenization. It is not a general Key Vault tier. [Payment HSM use cases](https://learn.microsoft.com/en-us/azure/payment-hsm/overview#typical-use-cases).
2. **[Tenancy and administration]** Each allocated device is single tenant, connected directly to the customer's VNet, and under the customer's exclusive administration; Microsoft has no access to customer data after allocation and zeroizes customer data when the device is released. [Payment HSM customer-control model](https://learn.microsoft.com/en-us/azure/payment-hsm/overview#customer-managed-hsm-in-azure).
3. **[Performance SKUs]** The included Thales payShield 10K Premium Package is available with `1` or `2` Local Master Keys and at `60`, `250`, or `2,500` cryptographic operations per second; the highest supported performance level is `2,500 CPS`. [Payment HSM SKU and licensing FAQ](https://learn.microsoft.com/en-us/azure/payment-hsm/faq#what-default-license-comes-with-azure-payment-hsm).
4. **[Network interfaces and concurrency]** Provisioning creates `2` host network interfaces and `1` management interface. Support for two host interfaces raises the documented maximum to `128` concurrent host connections, and both host interfaces must be in the same VNet. [Payment HSM network-interface update](https://learn.microsoft.com/en-us/azure/payment-hsm/whats-new#may-2023).
5. **[Network prerequisites]** Deployment requires a VNet and subnet delegated to `Microsoft.HardwareSecurityModules/dedicatedHSMs`; Microsoft examples use a `/24` HSM subnet and require registration of the `Microsoft.HardwareSecurityModules` and `Microsoft.Network` resource providers plus the Payment HSM features. [Create a Payment HSM prerequisites](https://learn.microsoft.com/en-us/azure/payment-hsm/create-payment-hsm#create-a-virtual-network-and-subnet).
6. **[High availability]** A production HA design requires `2` HSMs in one region, with one allocated to `stamp1` and the other to `stamp2`; the stamps span `2` availability zones. Two devices from the same stamp do not satisfy the documented HA design. [Payment HSM high-availability deployment](https://learn.microsoft.com/en-us/azure/payment-hsm/deployment-scenarios#high-availability-deployment).
7. **[Disaster recovery]** Regional disaster recovery requires additional HSMs in another region and normally fails over the entire application stack rather than making a Region 1 application call a Region 2 HSM, because cross-region HSM calls add latency. [Payment HSM disaster-recovery deployment](https://learn.microsoft.com/en-us/azure/payment-hsm/deployment-scenarios#disaster-recovery-deployment).
8. **[SLA and support]** Payment HSM has no device-specific uptime SLA; Microsoft assures network-level access under applicable Azure networking SLAs. A production environment without the documented HA setup is ineligible for Microsoft's highest-severity production support path. [Payment HSM SLA FAQ](https://learn.microsoft.com/en-us/azure/payment-hsm/faq#what-is-the-sla-for-payment-hsm-service) [Payment HSM support prerequisites](https://learn.microsoft.com/en-us/azure/payment-hsm/support-guide#availability).
9. **[Regional availability]** **[Limited regions — verify before specifying]** The July 2026 service support guide lists East US, West US, South Central US, Central US, North Europe, West Europe, Australia East, and Australia Southeast; capacity and onboarding qualification must be confirmed before committing the region. [Payment HSM current availability](https://learn.microsoft.com/en-us/azure/payment-hsm/support-guide#availability).
10. **[Certification distinction]** The payShield 10K devices are certified to FIPS 140-2 Level 3 and PCI HSM v3, and the Azure datacenters hosting the service maintain payment-focused PCI programs; this differs from the FIPS 140-3 Level 3 statements for current Managed HSM and Cloud HSM. [Payment HSM certification](https://learn.microsoft.com/en-us/azure/payment-hsm/overview#enhanced-security-and-compliance).
11. **[Operational ownership]** Customers apply security patches and firmware upgrades to allocated devices and work with Thales for device software/firmware support; Microsoft patches unallocated HSMs. The service price includes the premium-package licenses and an enhanced Thales support plan, but custom firmware is a separate Thales engagement. [Payment HSM support responsibility](https://learn.microsoft.com/en-us/azure/payment-hsm/support-guide#prerequisites).
12. **[Management dependencies]** Remote administration uses Thales payShield Manager, a Trusted Management Device, smart cards, and card readers. Customers must obtain the required Thales portal access and physical accessories before onboarding. [Payment HSM onboarding prerequisites](https://learn.microsoft.com/en-us/azure/payment-hsm/support-guide#prerequisites).
13. **[Topology limitation]** Payment HSM is not compatible with virtual WAN topologies or cross-region VNet peering in current documentation, so a generic global hub-and-spoke assumption can invalidate the network design. [Payment HSM current topology limitations](https://learn.microsoft.com/en-us/azure/payment-hsm/whats-new).

### Incompatibilities and mutual exclusions

If the workload requires ordinary secrets, certificate lifecycle, generic Azure PaaS CMKs, or nonpayment application keys, Payment HSM cannot replace Key Vault or Managed HSM because its device, command set, licensing, and certifications are purpose-built for payment cryptography. [Payment HSM use cases](https://learn.microsoft.com/en-us/azure/payment-hsm/overview#typical-use-cases) [Azure key-management selection guide](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose).

If two HSMs must form the documented in-region HA design, they cannot both use the same stamp; one must be on `stamp1` and one on `stamp2`. [Payment HSM HA stamp requirement](https://learn.microsoft.com/en-us/azure/payment-hsm/deployment-scenarios#high-availability-deployment).

### Edge cases and gotchas

- Releasing a commissioned Payment HSM permanently removes all customer data, keys, logs, and configuration from the device; it is a destructive decommissioning operation, not a pause. [Payment HSM decommissioning FAQ](https://learn.microsoft.com/en-us/azure/payment-hsm/faq#how-do-i-decommission-an-hsm).
- A stateless payment application model does not eliminate key backup requirements; customers own approved key backup and restore procedures and must test them across HA/DR devices. [Secure Payment HSM backup and recovery](https://learn.microsoft.com/en-us/azure/payment-hsm/secure-payment-hsm#backup-and-recovery).
- In December 2025 Microsoft upgraded the base firmware to `2.2b`; customers must validate firmware and optional-license compatibility rather than assume an on-premises payShield image is identical. [Payment HSM release history](https://learn.microsoft.com/en-us/azure/payment-hsm/whats-new#december-2025).
- The support guide currently lists Australia Southeast while the FAQ's shorter availability list omits it; treat region availability as a predeployment verification item rather than relying on a memorized list. [Payment HSM support-guide availability](https://learn.microsoft.com/en-us/azure/payment-hsm/support-guide#availability) [Payment HSM availability FAQ](https://learn.microsoft.com/en-us/azure/payment-hsm/faq#where-is-azure-payment-hsm-available).

### AZ-305 exam discriminator

Choose Payment HSM when the requirement names PIN generation/validation, EMV cryptograms, card issuing, 3-D Secure, payment tokenization, PCI PIN, or migration of payShield payment commands; those operations are explicitly excluded from the general-purpose HSM decision. [Azure key-management payment discriminator](https://learn.microsoft.com/en-us/azure/security/fundamentals/key-management-choose).

### Common trap

“Most secure HSM” is not the decision rule. Managed HSM can have a newer FIPS validation and still be the wrong answer because it does not implement the payShield payment command/certification ecosystem. [Payment HSM typical use cases](https://learn.microsoft.com/en-us/azure/payment-hsm/overview#typical-use-cases).

## Managed identities and workload identity federation

**Classification:** Core  
**Why it matters:** The architect should eliminate a credential before designing its storage and rotation whenever a supported workload can exchange a trusted identity for a Microsoft Entra access token.  
**Primary Microsoft source:** [Secretless authentication for Azure resources](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication)  
**Limits and quotas source:** [Workload identity federation considerations](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation-considerations)

### Deep technical facts / requirements

1. **[Authentication boundary]** A managed identity can request tokens only for resources that support Microsoft Entra authentication. When the target requires a password, account key, or non-Entra certificate, use the workload identity only to retrieve that unavoidable material from Key Vault. [Managed identity target-resource boundary](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication#azure-service-accesses-external-or-non-microsoft-entra-protected-resources).
2. **[System-assigned lifecycle]** A system-assigned managed identity belongs to exactly `1` Azure resource and is deleted with that resource; its lifecycle coupling prevents reuse but avoids an orphaned identity when the resource is removed. [Managed identity lifecycle comparison](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-managed-identities-work-vm).
3. **[User-assigned lifecycle]** A user-assigned managed identity is a standalone Azure resource that can be attached to multiple supported source resources and survives their deletion. It must be deleted explicitly, and its abandoned role assignments are not removed automatically. [Managed identity developer guidance](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview-for-developers) [Managed identity maintenance guidance](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#maintenance).
4. **[Internal credentials]** Azure internally issues and rolls the certificate used by the managed identity service principal; application code obtains tokens and never receives the identity's underlying credential. [How managed identities work](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-managed-identities-work-vm).
5. **[Same-tenant default]** For Azure service-to-service access within one tenant, Microsoft recommends managed identity plus `DefaultAzureCredential`; RBAC or the target's authorization model still determines what the token can do. [Same-tenant secretless pattern](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication#accesses-microsoft-entra-protected-resources-same-tenant).
6. **[Cross-tenant constraint]** A managed identity is not directly a multitenant application identity. Cross-tenant Azure workload access requires an application in the target model to trust the managed identity through federation rather than attempting to use the managed identity directly across tenants. [Cross-tenant managed-identity pattern](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication#accesses-microsoft-entra-protected-resources-across-tenants).
7. **[External workload flow]** Workload identity federation makes an app registration or user-assigned managed identity trust an external issuer such as GitHub, Kubernetes, or another cloud; the workload exchanges the external OIDC token for a Microsoft identity-platform access token without storing an Entra client secret or certificate. [Workload identity federation overview](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation).
8. **[Federation limit]** An app registration or user-assigned managed identity supports at most `20` federated identity credentials. The issuer-and-subject pair must be unique, and token `issuer`, `subject`, and `audience` values must match the configured credential. [Federated identity credential limits and matching](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation-considerations).
9. **[Preview scale option]** **[Preview]** Flexible federated identity credentials use a restricted expression language to match subjects and selected custom claims, which can reduce pressure on the `20`-credential limit; explicit issuer/subject/audience matching remains the GA baseline. [Flexible federated identity credentials preview](https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-flexible-federated-identity-credentials).
10. **[Directory-move incompatibility]** Moving a subscription to another Microsoft Entra directory breaks existing managed identities because their tenant objects are not updated. System-assigned identities must be disabled/re-enabled; user-assigned identities must be deleted, recreated, and reattached. [Managed identity directory-transfer issue](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/known-issues#transferring-a-subscription-between-microsoft-entra-directories).
11. **[Regional isolation]** A user-assigned identity's isolation scope defaults to `None`, allowing assignment to source resources across regions; setting it to `Regional` restricts source-resource assignment to the identity's region but does not restrict which target-resource regions the identity can access. [User-assigned identity regional isolation](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identities-isolation-scope).
12. **[Preview assignment restriction]** **[Preview]** User-assigned identity assignment restrictions default to an empty array, meaning unrestricted assignment to any supporting resource provider; restrictions can limit which source resource providers may attach the identity but do not limit its downstream targets. [Managed identity assignment restriction preview](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identities-assignment-restriction).
13. **[Authorization cache behavior]** Group-based RBAC changes for a managed identity can be delayed by token and authorization caching; Microsoft recommends assigning permissions directly to a user-assigned identity when fast, predictable permission changes matter. [Managed identity authorization limitation](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#limitation-of-using-managed-identities-for-authorization).

### Incompatibilities and mutual exclusions

If the destination cannot validate Microsoft Entra tokens, a managed identity cannot replace the destination's password, key, or certificate; it can only authenticate the Azure workload to Key Vault so the application can retrieve that unavoidable credential. [Secretless non-Entra target pattern](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication#azure-service-accesses-external-or-non-microsoft-entra-protected-resources).

If one application or user-assigned identity needs more than `20` explicit federated trust relationships, GA federated identity credentials cannot represent them all; split the identity design or evaluate the preview flexible-credential capability with its preview risk. [Workload identity federation limit](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation-considerations) [Flexible credential preview](https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-flexible-federated-identity-credentials).

### Edge cases and gotchas

- The `principalId` identifies the managed identity service principal for role assignments, while `clientId` identifies a user-assigned identity in application/token-selection code; confusing them causes deployment or runtime failures. [Managed identity developer identifiers](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview-for-developers#creating-a-managed-identity).
- Deleting a managed identity leaves Azure role assignments that show `Identity not found` or `ObjectType=Unknown`; they consume role-assignment capacity until removed. [Managed identity maintenance guidance](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#maintenance).
- A shared user-assigned identity couples the blast radius of every attached source resource; reuse is a lifecycle capability, not an instruction to share one identity across unrelated applications. [Managed identity security guidance](https://learn.microsoft.com/en-us/entra/architecture/service-accounts-managed-identities).
- Flexible subject matching and identity assignment restrictions are both preview capabilities in July 2026 and should not be silently treated as stable GA exam defaults. [Flexible federated credentials preview](https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-flexible-federated-identity-credentials) [Managed identity assignment restriction preview](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identities-assignment-restriction).

### AZ-305 exam discriminator

When both source and target support Microsoft Entra authentication, managed identity or workload identity federation outranks “store the credential in Key Vault” because the credential can be removed entirely; Key Vault becomes the fallback for an unavoidable non-Entra credential. [Secretless authentication decision patterns](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication).

### Common trap

A managed identity authenticates the caller but grants no access by itself. The target still requires RBAC, database permissions, an application role, or another authorization grant. [Secretless same-tenant authorization pattern](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/secretless-authentication#accesses-microsoft-entra-protected-resources-same-tenant).
