Coverage notes:

- Coverage is centered on one primary documentation set. Azure Key Vault carries most of the task, but a complete recommendation also needs the key management decision guidance in Azure security fundamentals, the identity documentation that removes secrets altogether, and the framework guidance that supplies the tradeoff wording.
- Download Azure Key Vault and Azure security fundamentals first. Add Managed HSM and Cloud HSM only when the scenario mentions FIPS 140-3 Level 3, single tenancy, key sovereignty, PKCS#11, or migration from an existing on-premises HSM.
- Separate four decisions before choosing a service: which object type is being stored, what hardware protection and compliance level is required, how the consuming workload authenticates to the store, and how the material is rotated, renewed, and revoked.
- The decisive constraint in service selection is object type. Managed HSM stores keys only, so any scenario that also names passwords, connection strings, or TLS certificates rules it out as the sole solution. Cloud HSM is IaaS-only and does not integrate with Azure PaaS or SaaS customer-managed key scenarios.
- Key Vault Premium and Managed HSM both give HSM-backed keys. Premium is multi-tenant and billed transactionally with a per-key charge; Managed HSM is single-tenant, adds key sovereignty and a customer-controlled security domain, and bills at a fixed hourly rate. Cost and tenancy, not raw capability, usually decide between them.
- Prefer a managed identity or workload identity federation over any stored credential. Recommend a vault only for material that genuinely cannot be replaced by a token, and treat Key Vault as the store for the remaining secrets rather than the default answer to every credential question.
- Vault topology is a scored design decision. One vault per application, per region, per environment limits blast radius and matches RBAC scope; a single shared vault is normally the wrong answer. Multitenant SaaS adds one vault per tenant.
- Azure RBAC is the current permission model. Legacy access policies lack PIM support and should not appear in a new design. Note that object-scope RBAC assignments only support read operations, so administrative delegation requires vault-level scope.
- Distinguish configuration from secrets. App Configuration holds settings and feature flags and stores only a URI reference to a Key Vault secret; the application authenticates to both services separately. Key Vault is not a data store or a configuration store.
- Rotation differs by object type and this is easy to get wrong. Keys support a native rotation policy, certificates support automatic renewal with integrated CAs, but secrets require an Event Grid and Azure Functions pattern, with a dual-credential variant when the target system must stay available across the rotation.
- Availability and recoverability are lightly covered here but testable. Soft delete plus purge protection, Key Vault backup, Managed HSM manual cross-region disaster recovery, and the fact that disabling a KEK takes dependent services such as SQL TDE and CMK-encrypted storage offline are all realistic scenario hooks.
- The Azure Key Vault provider for Secrets Store CSI Driver on AKS, Microsoft Defender for Key Vault, Key Vault private endpoints and firewall design, Azure Policy compliance controls, confidential computing secure key release, Azure Dedicated HSM as the retiring predecessor to Cloud HSM, and Azure Payment HSM for PCI PIN processing are adjacent topics worth one pass but should not dominate this map.
